# MILESTONES – משחק "סיימון" (Simon)

> **מקורות:** `PRD.md` (דרישות), `ARCHITECTURE.md` (ארכיטקטורה ופריסה), `DESIGN.md` (מסכים ועיצוב).
> **שפת הממשק:** עברית בלבד, RTL. כל טקסט ממשק המצוטט במסמך זה הוא הטקסט המדויק שיוצג למשתמש.
> **היקף המסכים:** המימוש כולל מסך בית וחלון סיכום בלבד. לוח הנקודות (Scoreboard) הוא רכיב בתוך מסך הבית, ואין מסך אודות ואין אלמנט ניווט. כל שלושת המסמכים (PRD, ARCHITECTURE, DESIGN) מיושרים בנושא זה.
> **סביבות:** ARCHITECTURE מגדיר סביבה אחת בלבד (Production ב-GitHub Pages) וללא Backend וללא Database. לכן אין סביבת Development בענן ואין Database Migrations. כל הבדיקות רצות מקומית (`npm run dev`, `npm test`, `npm run build` + `npm run preview`), אפשר גם מטלפון שמחובר לאותה רשת.
> **בדיקות בכתובת החיה:** רק ב-M0 (הפריסה עצמה), ב-M4 (התקנה אמיתית בטלפון) וב-M5 (אימות סופי). באבני דרך אלה הדחיפה ל-`main` נעשית לפני האישור, ורק אחרי אישור מפורש של המשתמש. ב-M1 עד M3 הבדיקה מקומית, והאתר החי מתעדכן כשהמשתמש מאשר ודוחף.

## M0 – Foundation ופריסה 🟡

**מטרה:** להקים שלד פרויקט ו-Pipeline פריסה אוטומטי, כך שמהיום הראשון כל שינוי מגיע לאתר חי. זה תנאי מקדים לכל שאר העבודה, והוא נותן לבעלים כתובת לבדיקה מכל מכשיר.

**מה יש לממש:**
- Repository ב-GitHub עם ענף `main`, ומבנה התיקיות לפי סעיף 4 ב-ARCHITECTURE (`src/ui` כולל Home Screen, Board, Scoreboard ו-Overlay).
- פרויקט Vite 8 עם TypeScript 6.x במצב `strict`, Node.js 24 LTS ו-npm, כשהגרסאות נעולות ב-`package-lock.json`.
- `index.html` עם `lang="he"`, `dir="rtl"`, תג `viewport` עם `viewport-fit=cover`, וגובה לפי `100dvh`.
- ערכות העיצוב כ-CSS Custom Properties לפי `DESIGN.md` סעיף 2: צבעי משחק (Lit / Idle / Edge), צבעי בסיס (Ink, Bezel, Surface, Line, Muted, Cloud, White, Board Housing), משפחת הגופנים `Arial, Helvetica, sans-serif`, סולם הרדיוסים והמרווחים.
- מודול `Strings` עם כל טקסטי הממשק מ-`DESIGN.md` ("טקסטי הממשק").
- Header במסך הבית: "סיימון" בימין ו-Pill "שלב 1" בשמאל, וקו מפריד, לפי ה-Mockup.
- הגדרת Vitest, עם בדיקה בסיסית אחת שעוברת.
- `base` של Vite שמוזרק מתוך שם ה-Repository ב-CI, ו-`/` בהרצה מקומית.
- Workflow בקובץ `.github/workflows/deploy.yml`: `npm ci`, `tsc --noEmit`, `vitest`, `vite build`, העלאת `dist` ופריסה ל-GitHub Pages. הרשאות, `concurrency` והפעלה ב-Push ל-`main` וידנית, לפי סעיף 3ג ב-ARCHITECTURE.

**פעולות שהמשתמש מבצע בהדרכה צעד אחר צעד:**
1. יצירת Repository ציבורי ב-GitHub ומסירת שמו ל-AI.
2. חיבור התיקייה המקומית ל-Repository ודחיפה ראשונה (`push`).
3. ב-Settings ← Pages ← Source: בחירה ב-**GitHub Actions**.
4. הפעלת ה-Workflow ווידוא שהאתר עלה בכתובת `https://<שם-משתמש>.github.io/<שם-repo>/`.

**תוצר מצופה:** כתובת ציבורית שבה נפתח מסך בית ראשוני בעיצוב כהה עם הכותרת "סיימון" ו-Pill "שלב 1", מיושר RTL.

**Definition of Done:**
- [ ] `npm ci`, `npx tsc --noEmit`, `npm test` ו-`npm run build` עוברים ללא שגיאות.
- [ ] `npm run dev` מציג את מסך הבית עם הכותרת וה-Pill במיקומים כמו ב-Mockup (כותרת בימין, Pill בשמאל).
- [ ] ה-Workflow רץ בהצלחה ב-GitHub Actions והאתר נטען בכתובת החיה, כולל קבצי JS ו-CSS (בלי שגיאות 404 בגלל ה-`base`).
- [ ] ב-Workflow, שלבי בדיקת הטיפוסים והבדיקות רצים לפני ה-Build והפריסה, כך שכשל בהם עוצר את הפריסה (מאומת בקריאת קובץ ה-Workflow).

## M1 – משחק שלם

**מטרה:** לתת לשחקן את הליבה של המוצר: ללחוץ "התחל" ולשחק משחק סיימון אמיתי של עד 10 שלבים, עם אור וצליל. זה הערך המרכזי של המוצר, ולכן הוא נבנה ונבדק לפני כל תכונה נלווית.

**מה יש לממש:**
- **לוח המשחק** לפי `DESIGN.md`: עיגול בארבעה רבעים בפריסה קבועה (ירוק למעלה-שמאל, אדום למעלה-ימין, צהוב למטה-שמאל, כחול למטה-ימין) עם `dir="ltr"`, מעטפת כהה, וכפתור "התחל" עגול ירוק במרכז. מצבי **Idle** ו-**Lit** (כולל Glow) לפי הסעיף "מצבי הרבעים".
- **Game Engine** (ללא תלות ב-DOM, באודיו או באחסון), עם מכונת המצבים `Idle ← ShowingSequence ← AwaitingInput ← GameOver`: יצירת רצף אקראי שגדל בצבע אחד בכל שלב, הצגתו מההתחלה בכל שלב, בדיקת כל לחיצה מול הרצף, כישלון מיידי בלחיצה שגויה, וניצחון בהשלמת שלב 10.
- **Config:** ארבעת הצבעים, 10 שלבים, הדלקת צבע של כ-500 אלפיות השנייה ומרווח של כ-200 אלפיות השנייה בין צבעים.
- **Audio Service** עם Web Audio API: ארבעה צלילים שונים, בערכי פתיחה כ-262, 330, 392 ו-523 הרץ עם עלייה וירידה קצרות של עוצמה. ה-AudioContext מופעל בלחיצה על "התחל".
- **אינטראקציה:** קלט באמצעות `pointerdown`, `touch-action: manipulation` ומניעת בחירת טקסט ותפריט לחיצה ארוכה על הרבעים. לחיצות בזמן הצגת רצף מתעלמות. לחיצות מהירות נבדקות לפי סדר ההגעה.
- **Pill "שלב N"** בכותרת, שמציג את השלב הנוכחי.
- **כפתור "התחל"** אינו זמין בזמן משחק פעיל.
- ההחלטות הפתוחות 1, 2 ו-3.
- **סיום משחק זמני:** בסוף משחק (כישלון או ניצחון) המצב חוזר ל-`Idle` והכפתור "התחל" זמין שוב. חלון הסיכום מגיע ב-M2.

**תוצר מצופה:** משחק סיימון שעובד מקצה לקצה במסך הבית, בדפדפן במחשב ובטלפון (בהרצה מקומית).

**Definition of Done:**
- [ ] בדיקות Vitest ל-Game Engine עוברות, ומכסות: רצף באורך N בשלב N; הרצף של שלב N+1 מתחיל ברצף של שלב N; כישלון בלחיצה שגויה אחת; ניצחון רק בהשלמת שלב 10; התעלמות מקלט ב-`ShowingSequence`; סדר טיפול בלחיצות רצופות. הבדיקות משתמשות במחולל אקראי מוזרק.
- [ ] משחק מלא עד שלב 10 אפשרי, ונבדק ידנית בדפדפן מקומי (ובטלפון באותה רשת, אם אפשר).
- [ ] כל אחד מארבעת הרבעים מואר ומשמיע צליל ייחודי, גם בהצגת הרצף וגם בלחיצת המשתמש, ומשוב הלחיצה מיידי.
- [ ] לחיצה על רבע בזמן הצגת רצף אינה משפיעה על המשחק.
- [ ] לחיצה שגויה אחת מסיימת את המשחק מיד.
- [ ] ה-Pill מציג "שלב N" נכון בכל שלב.
- [ ] "התחל" אינו ניתן להפעלה בזמן משחק.
- [ ] בזמן משחק ברור לשחקן מתי תורו (לפי ההחלטה שאושרה).
- [ ] Refresh באמצע משחק מחזיר למסך בית במצב התחלתי.
- [ ] כשהצליל לא מושמע (למשל מכשיר שקט), המשחק ממשיך לעבוד עם משוב חזותי בלבד.
- [ ] פריסת הצבעים של הלוח זהה ל-Mockup גם עם `dir="rtl"` על המסמך.

## M2 – חלון סיכום ו"שחק שוב"

**מטרה:** לסגור את חוויית המשחק. השחקן מבין מיד איך הלך לו ויכול להתחיל משחק חדש בלחיצה אחת, כך שהוא נשאר בלולאת משחק.

**מה יש לממש:**
- **חלון סיכום (Overlay)** מעל מסך הבית לפי `DESIGN.md` סעיף 1.2: Scrim שחור ב-53%, כרטיס Surface ממורכז (324×300) עם צל וקו מתאר.
- כותרת בכישלון: "הפסדת בשלב N", כש-N הוא השלב שבו נגמר המשחק.
- כותרת בניצחון (בשלב 10): לפי ההחלטה הפתוחה 5, באותו מבנה.
- כפתור ראשי ירוק "שחק שוב", שסוגר את החלון ומתחיל משחק חדש. זו הפעולה היחידה בחלון, ואין בו קישורים נוספים.
- חיבור אירוע סיום המשחק מה-Game Engine לפתיחת החלון. מסך הבית נשאר גלוי ומעומעם מאחוריו.
- ה-Badge "שברת שיא אישי" אינו מוצג בשלב זה, והוא מתווסף ב-M3.

**תוצר מצופה:** לולאת משחק רציפה: התחל ← משחק ← סיכום ← "שחק שוב" ← משחק חדש.

**Definition of Done:**
- [ ] בסיום כל משחק, בכישלון ובניצחון, נפתח חלון הסיכום עם השלב הנכון.
- [ ] החלון נראה כמו ה-Mockup "חלון סיכום": מידות, צבעים, צל, Scrim וטקסטים.
- [ ] "שחק שוב" סוגר את החלון ומתחיל משחק חדש משלב 1, ללא שאריות מהמשחק הקודם.
- [ ] לא ניתן ללחוץ על רבעי הלוח או על "התחל" בזמן שהחלון פתוח.
- [ ] ניצחון בשלב 10 מציג את הכותרת שאושרה.
- [ ] אין בחלון קישור או ניווט למסך אחר.
- [ ] בדיקות Vitest שנוספו ל-M1 ממשיכות לעבור.

## M3 – ניקוד ושיא אישי

**מטרה:** לתת לשחקן סיבה לחזור, כלומר שיא אישי ורשימת משחקים אחרונים שנשמרים במכשיר. זהו החלק של "השחקן שמתחרה בעצמו" מה-PRD, והוא כולל גם את שמירת הנתונים ואת התצוגה שלהם.

**מה יש לממש:**
- **Storage Service:** מפתח אחד ב-Local Storage בשם `simon.scores.v1`, עם מבנה `StoredScores` (`version`, `best`, `recent`) ו-`GameResult` (`levelReached`, `won`), לפי סעיף 2ד ב-ARCHITECTURE.
- **כללי כתיבה:** כתיבה רק בסיום משחק שהושלם. שיא חדש רק אם `levelReached` גדול מהשיא הקודם (שיא שווה אינו שבירה). פריט חדש נכנס בראש הרשימה, ועד 5 פריטים נשמרים.
- **אימות בקריאה:** נתונים פגומים או גרסה לא מוכרת מאופסים למצב ריק ללא קריסה. כשהאחסון חסום או נכשל, הכתיבה נבלעת והמשחק ממשיך כרגיל.
- **Scoreboard במסך הבית** לפי `DESIGN.md` סעיף 1.1: כרטיס שיא ("שיא אישי" ו-"7 מתוך 10" בצהוב), כותרת "משחקים אחרונים", ועד 5 שורות "שלב N" מהחדש לישן. השורה ששווה לשיא מודגשת בקו מתאר `#E09400`.
- **Badge "שברת שיא אישי"** בחלון הסיכום, רק כשנשבר שיא.
- ההחלטות הפתוחות 4, 6 ו-7: התנהגות הלוח בזמן משחק, המצב הריק, הודעת האחסון הלא זמין והדגשת שוויון.
- עדכון הלוח מיד בסיום משחק, כך שהוא מדויק כשהחלון נסגר.

**תוצר מצופה:** אחרי כל משחק, השיא והרשימה מתעדכנים, נשמרים במכשיר וזמינים בפתיחה הבאה.

## M4 – PWA ו-Offline

**מטרה:** לאפשר לשחקן להתקין את המשחק על מסך הבית ולשחק בכל מקום, גם בלי חיבור. זה מקיים את הדרישה המרכזית של ה-PRD לגבי שימוש במובייל ללא חיבור קבוע.

**מה יש לממש:**
- **vite-plugin-pwa 1.3 ומעלה** באסטרטגיית `generateSW`, עם Precache לכל קבצי הבנייה, כולל `png` ו-`svg` ב-`globPatterns`.
- **Web App Manifest:** שם "סיימון", `lang: he`, `dir: rtl`, `display: standalone`, `orientation: portrait`, צבע ערכת נושא ורקע כהים לפי `Ink` (`#0F1110`), ו-`start_url` ו-`scope` לפי ה-`base` של האתר.

## Development Execution Rules – כללי ביצוע לפיתוח (ל-AI המפתח)

1. **סדר:** יש לפתח את ה-Milestones לפי הסדר M0 עד M5, כפי שהוגדר במסמך זה.
2. **עצירה בסוף כל Milestone:** לאחר השלמתו יש לעצור את הפיתוח ולהציג למשתמש:
   - את התוצר שהושלם (כתובת חיה או הוראות הרצה, וצילומי מסך כשרלוונטי);
   - טבלה של כל סעיפי ה-Definition of Done עם תוצאה (עבר או נכשל) וראיה (פלט בדיקות, צילום, קישור);
   - רשימת סעיפים שדורשים בדיקה ידנית של המשתמש, אם יש.
3. **אין להתחיל Milestone הבא ללא אישור מפורש של המשתמש.** אישור על Milestone אחד אינו מתיר את הבא אחריו.
4. **אין לסמן סעיף כ"עבר" בלי שאומת בפועל.** סעיף שלא ניתן לאמת (למשל בדיקה במכשיר אמיתי) מסומן כ"ממתין לבדיקת המשתמש".
5. **החלטות פתוחות:** פרט המופיע בטבלת "החלטות פתוחות" מוצג למשתמש בתחילת ה-Milestone המצוין, עם הצעה אחת, וממומש רק אחרי אישור. אין להמציא עיצוב או טקסט במקומו.
6. **היקף:** אין להוסיף מסכים, פיצ'רים, התנהגויות או רכיבי UI שאינם מופיעים ב-PRD, ב-ARCHITECTURE וב-DESIGN. אין לבנות מסך "אודות" או סרגל ניווט, ואין להוסיף רכיבים ש-DESIGN מגדיר כ"אינם במסכים" (כפתור משני וכפתורי אייקון).
7. **סדר עדיפויות במקרה של סתירה:** `PRD.md` לדרישות המוצר, `ARCHITECTURE.md` להחלטות טכניות, ו-`DESIGN.md` לכל מה שקשור למסכים ולעיצוב. במקרה של סתירה שאינה ברורה, יש לעצור ולשאול את המשתמש.
8. **סביבה:** אין Backend, Database או סביבת Development בענן. כל שינוי נבדק מקומית לפני דחיפה ל-`main`, שמפעילה פריסה אוטומטית ל-Production.
9. **מצב עובד:** בסוף כל Milestone האפליקציה בונה בהצלחה והבדיקות עוברות, ואחרי הדחיפה האתר החי עובד. אין להשאיר ענף או קוד שבור.
